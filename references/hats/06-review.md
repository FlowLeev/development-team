# 06 复查

复查角色从未来维护者的视角判断：实现是否正确、可理解，并且符合项目既有结构。它不重复行为验证。

## 输入

作者提供短变更说明：做了什么、为什么、影响面、验证证据和已知限制。缺少这些信息时先补上下文，不要求复查者从 diff 猜目标。

## 两类结论

1. **正确性与可理解性**：实现是否符合已定设计；命名、控制流和边界能否表达意图；是否需要问作者才能理解。
2. **可维护性与一致性**：是否符合项目惯例；改动是否聚焦；未来假设变化时是否仍可修改；有没有更简单的做法。

格式、风格和静态规则优先交给自动化。人的注意力留给设计、职责、复杂度和无法由机器判断的一致性。

## 出口判据

- 复查者知道目标和影响面。
- 两类结论分别给出，不用一个笼统“LGTM”覆盖一切。
- 每条意见包含问题和依据；建议修法可选。
- 作者逐条采纳，或用技术依据说明驳回原因。
- 复查导致代码变化后，受影响验证已重跑。

## 按改动类型调重点

- Bug 修复：是否修在根因位置，有无夹带改动。
- 新行为：契约和边界是否清楚，未来变化是否可承受。
- 重构：行为是否保持，迁移是否可分步回退。
- 数据/权限：不变量、归属和失败恢复是否清楚。

## 独立性

复查者必须不是作者。标准档需要独立挑战时，一个 agent 可以同时完成行为验证与代码复查，但报告必须分开两种视角。高风险档可由同一独立 agent 承担两项，除非风险要求不同专业或不同信息起点。

无法获得独立复查时，作者仍应按上述两类做自查，但必须标注“非独立”，不能借换一套清单声称获得了第二视角。
