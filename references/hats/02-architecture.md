# 02 架构

架构角色决定改动放在哪里、哪些边界不能破坏，以及失败后是否仍可恢复。它先理解既有系统，再提出最小充分设计。

## 调查顺序

1. 读入口指令、架构记录和相关契约。
2. 沿真实调用链和数据流定位职责，不只看报错文件。
3. 找现有相似实现和项目惯例。
4. 把事实、推断和待验证假设分开。

## 出口判据

- 影响的模块、调用方、数据和运行面已识别。
- 放置与职责边界明确，能解释为什么属于这一层。
- 公共契约、兼容性、已存数据和安全约束已列出。
- 推荐设计有证据；关键假设有最小验证或明确风险标记。
- 可逆性与失败恢复已考虑。
- 偏离既有决定或用户约束时已请求同意。

## 实施简报中的架构部分

- **影响面**：谁会受到什么变化。
- **放置与边界**：在哪层修改，对外接口和数据流是什么。
- **不能改变的约束**：契约、不变量、兼容性和安全边界。
- **取舍**：为了什么优先项接受了什么代价。
- **风险与恢复**：最可能怎样失败，是否可撤回。

## 项目目录与代码放置

从零创建项目、增加新的应用/包/服务、调整模块边界或重组目录时，读取 `../project-structure.md`。进入目录设计前，先区分工作区根、仓库根、项目根和包/应用/服务根；当前 `cwd` 本身不是项目根证据。该参考提供的是目录设计判断，不是固定模板：先遵循语言、框架、构建工具和现有仓库惯例，再按职责、变化原因和交付边界组织内容。

局部功能或 Bug 修复不应顺手重排目录。只有现有结构已经造成错误放置、变化放大、所有权含混或构建/发布问题，而且重组属于用户要求或已批准范围时，才修改项目布局。

不要为每次改动制作完整架构文档。只有一个决定会持续约束未来工作、无法从代码重建动机时，才按项目已有形式写决策记录；至少包含背景、决定和后果。被取代的决定保留历史并指向新决定。

可自动检查的重要约束优先固化为测试或静态检查，但检查本身也有维护成本。只有它能长期防止真实风险时才新增，不为了满足流程制造脚本。

## 停止与回退

- 发现正确方案需要改变已批准范围 → 回到定义。
- 发现技术路径依赖未验证前提 → 先做隔离探针。
- 发现会破坏契约、数据或安全边界 → 升档并进入用户决策门。
- 只是实现细节不同、但不改变已定结果 → 工程方自行判断并记录理由，无需打断用户。
