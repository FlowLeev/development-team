# development-team

一个面向所有代码开发的 Agent Skill。它解决的不是“agent 不会写代码”，而是 agent 在理解问题、系统上下文、边界和约束之前就开始实现，随后依靠连续补丁弥补早期设计缺失的问题。简单改动走轻档，复杂度和风险越高，调查与验证才相应增加。

核心流程只有三道门：**理解 → 决策 → 证据**。八个角色文件按触发增量加载，不要求每个任务机械走完一套团队仪式。清晰、局部、可逆的需求只加载实现角色；用户体验作为验证角色下的纯黑盒子模式，仅在新增完整用户流程或公开工具体验发生实质变化时加载。

## 适用范围

适合任何实际创建或修改代码的任务，包括：

- 拼写、格式化和其他明确的机械代码编辑
- 从零创建项目、应用、服务或工具，以及初始化代码库和基础架构
- 新功能、Bug 修复和行为变更
- 跨模块重构、迁移与系统集成
- 测试、脚本以及项目、构建、部署和运行配置修改

不适合：

- 只读解释、咨询或调查
- 不包含实现工作的独立代码审查

## 安装

将本仓库放入 Agent 已注册的 skills 目录。例如：

```bash
git clone git@github.com:FlowLeev/development-team.git ~/.dsh/skills/development-team
```

其他兼容 Agent Skills 的客户端，请将仓库放入其 skills 目录，或注册本仓库父目录。客户端应先发现 `SKILL.md` 的 `name` 与 `description`，选中后再加载完整正文和所需 references。

## 让所有代码开发都先考虑本 skill

自动选择依赖模型根据 description 做路由，不能当作绝对保证。如果希望它成为默认开发纪律，可在项目级或全局 agent 指令中加入：

```markdown
对于任何会创建或修改代码、测试、脚本或项目/构建/运行配置的开发任务，
在第一次写入前加载 development-team skill，由 skill 内部按风险决定流程重量。
上下文压缩或从压缩摘要恢复后，在继续写入前重新加载该 skill。
只读解释和不包含实现工作的独立代码审查不触发。
```

这条短规则负责稳定路由；完整工作方法仍保留在 skill 中，避免长期占用上下文。

## 最小加载

- 清晰、局部、可逆且不碰契约、数据、安全和运行面的任务：只读实现角色。
- 出现目标取舍、边界不明、多步骤依赖、系统性验证或运行影响时：只增加对应角色。
- 新增完整用户流程，或用户入口、任务完成、结果理解与错误恢复体验发生实质变化时：验证角色再按需加载纯黑盒用户体验规则。
- 上下文压缩后重新加载主 skill，但不自动加载全部 references。
