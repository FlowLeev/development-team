# 08 交付

交付角色把已完成工作的决策和证据压缩成用户与未来维护者能直接使用的说明。它不重复工具流水，也不产生新的技术结论。

## 出口判据

- 第一段先说结果，而不是过程。
- 说明改了什么、为什么，以及是否偏离实施简报。
- 给出关键验证证据及其来源：作者验证、独立挑战或非独立自查。
- 面向用户的产品说明用户 agent 实际完成了哪些任务、主要摩擦及复测结果；未执行时明确标为未验证。
- 明确未验证面和已知限制，让读者能判断是否可接受。
- 有运行影响时写回滚/恢复方式；没有运行影响时不制造形式化回滚章节。
- 改动影响兼容性或发布语义时明确说明。

## 按档位伸缩

轻档通常三部分足够：改了什么；怎么验证；还有什么没验证。

标准档增加：影响面、关键设计决定、兼容性和回退方式。

高风险档增加：用户批准的范围、恢复演练结果、独立验证来源、迁移/运行风险和明确的使用条件。

## 面向读者

- 使用者关心如何使用、限制和失败时怎么办。
- 维护者关心放置、契约、动机和如何复验。
- 受影响者关心兼容性、迁移和何时必须行动。

同一说明可以服务多个读者，但应先给共同结论，再按需要分层，不要把提交记录或完整命令输出直接倒给用户。

## 持久化边界

交付说明首先存在于当前对话、变更请求或项目已有交付载体。只有未来无法从代码与测试重建的决定、跨会话状态、重要限制或运行约束才必须写入项目记录。

不要为每个轻档修复新建永久文档。项目已有 changelog、ADR、状态文件或发布说明约定时遵循它们；没有且确有长期价值时，先提议位置再创建。

## 独立读者检查

高风险交付或面向多人接手的长任务，可以让未参与实现的 agent 只读交付说明，检查它能否回答：改了什么、如何验证、失败后怎么办。普通任务不强制进行这一步。
