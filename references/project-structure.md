# 项目目录与代码放置

本参考用于从零创建项目、增加新的应用/包/服务、调整模块边界，或明确要求重组目录的任务。普通功能和 Bug 修复不因本文件自动扩大为目录重构。

## 先定位真正的项目根

不要把 agent 的工作区目录、当前 `cwd`、IDE workspace 或挂载目录自动当成项目根目录。工作区可能只是多个仓库的上层容器，也可能包含一个仓库中的多个项目、包、应用或服务。

写入前先区分：

- **工作区根**：工具允许访问或挂载的范围，不代表代码归属边界；
- **仓库根**：版本控制边界；
- **项目根**：共享主要构建、配置、测试或部署生命周期的单元；
- **包/应用/服务根**：monorepo 中拥有局部源码、测试和配置的交付或所有权单元。

这些根目录可以重合，但不能未经调查就假定重合。按以下证据定位本次任务的目标根目录：

1. 用户明确指定的路径、项目或模块；
2. `AGENTS.md`、`README`、贡献指南等入口指令及其适用范围；
3. Git 边界，以及 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`pom.xml`、`*.sln`、workspace 配置等清单；
4. 构建、测试、导入、部署和发布配置实际从哪里解析；
5. 相邻目录是否属于独立项目，避免把无关内容纳入本次操作。

调查范围应围绕用户给出的路径和相关祖先、子目录逐步展开，不要无界扫描整台机器。所有命令和写入都在已确认的目标根目录或其明确子目录中执行；不要因为 shell 恰好位于工作区根，就在那里初始化 Git、创建 manifest 或散落源码。

对于从零创建项目：用户指定目标目录时遵循该目录；若只给出一个包含其他内容的工作区，应使用语义明确的项目子目录。只有空目录或用户明确指定为项目根的目录，才直接作为新项目根。目录名称或位置会影响可见结果、可能覆盖或混入既有文件时，先请求用户确认。

对于 monorepo：仓库根负责 workspace 级配置，具体包、应用或服务根负责局部实现；代码放置应跟随实际构建、发布和所有权边界。若目标根不显然，在实施简报中明确说明采用的根目录及判断依据。

## 先确定约束，再画目录树

按以下顺序调查：

1. 读取语言、框架、包管理器、构建工具和部署平台的惯例。
2. 读取仓库已有结构、导入路径、测试发现规则、发布清单和生成配置。
3. 识别独立交付单元、模块职责、变化原因、所有权和公共契约。
4. 区分开发者维护的源文件、第三方内容、生成产物、运行数据和公开静态资源。
5. 只有目录选择会影响实现时，才在实施简报中给出最小目录树和放置理由。

现有项目的惯例优先于本参考。偏离惯例必须解决一个明确问题；不要为了“看起来更规范”批量移动文件。

## 根目录表达仓库级职责

根目录只放仓库级入口、配置和具有清晰职责的一级目录。常见职责包括：

- 应用、服务或可独立发布的包；
- 产品源代码；
- 测试与测试资源；
- 文档；
- 构建、开发和维护工具；
- 面向用户的静态资源；
- 生成物或发布输出。

具体名称由生态决定，例如 `src`、`test`/`tests`、`doc`/`docs`、`tool`/`tools`、`app`/`apps` 都可能合理。名称应简洁、一致、容易被当前生态识别；不要把单复数或某个历史缩写当成跨项目硬规则。

根目录不应混入只能服务某个业务模块的内部文件。单体、多包仓库和多服务仓库的一级划分不同，不要强迫它们共享同一模板。

## 源代码优先按业务能力和变化原因组织

业务代码通常按领域、能力、功能或共同变化原因聚合，而不是先按控制器、模型、工具函数等技术类型把相关行为拆散。判断标准是：完成一次需求变更时，维护者是否能在一个清晰边界内理解和修改大部分相关内容。

以下情况可以按技术类型组织：

- 框架明确要求固定目录；
- 内容本身就是跨业务的技术层；
- 生成器、编译器或发布工具依赖该结构；
- 团队已有稳定惯例，改变它的成本高于收益。

目录层级应与真实边界对应。文件过多时先问是否存在可命名的子领域或职责，不要只增加 `misc`、`utils`、`common` 等无所有权的收纳目录。

## 共置还是集中

实现、测试、样式、模板、fixture 和模块私有资源可以共置，也可以由工具链集中管理。选择取决于它们是否一起变化、是否共享所有权，以及测试和构建工具的发现规则。

- 只服务一个模块的资源优先靠近该模块。
- 多个模块真正共享且拥有稳定契约的内容才进入共享位置。
- “以后可能复用”不足以创建公共目录。
- 公共目录中的内容应有明确调用方、责任边界和移除条件。

## 区分源文件、依赖和生成物

- 第三方依赖由包管理器、vendor 机制或平台工具管理；不要直接修改缓存或生成的依赖副本。
- 必须维护的第三方分支应进入有来源、版本和更新策略的受控位置，而不是伪装成项目自有代码。
- 构建输出、代码生成结果和派生资源应有明确生成命令与权威来源。
- 生成物默认不手工编辑；是否提交版本库由发布、部署和可复现构建要求决定。
- 源目录不等于发布目录。测试、文档和源码是否随制品发布，由制品类型与用户需求决定，不能统一规定删除。

## 目录变更的兼容性

重组目录前检查：

- 公共导入路径、包导出、插件发现和反射扫描；
- 测试、lint、构建、代码生成和部署配置；
- 文档链接、脚本、CI、容器构建上下文和忽略规则；
- 大小写敏感文件系统、路径长度和跨平台分隔符；
- Git 历史可读性以及是否能分步迁移。

如果目录移动会改变公共契约，先设计兼容层、迁移路径或版本边界。不要把大规模移动夹带进无关功能提交。

## 推荐的输出尺度

只有任务涉及项目结构时才输出目录方案，通常包括：

1. 一棵只展开关键边界的短目录树；
2. 每个非显然目录的一句话职责；
3. 公共接口、共享内容和生成物的放置规则；
4. 与框架默认值或既有结构不同之处及理由；
5. 若重组现有项目，迁移顺序和验证方法。

不要列出尚未需要的空目录，也不要为假设中的未来模块提前搭建层级。

## 来源与适用边界

本参考受 EFE《[项目目录结构规范](https://github.com/ecomfe/spec/blob/master/directory.md)》启发，保留了“根目录按职责划分、业务代码优先按业务逻辑组织、区分源代码与内容/生成资源”等耐久思想。

原规范面向特定时期的前端工程，包含 `dep`、`swf`、特定加载器、强制单数目录名和发布时删除开发目录等时代与工具链约束。本参考对这些内容作了跨语言、跨框架改写，不把原文的具体目录名和 MUST/MUST NOT 直接套用到现代项目。
