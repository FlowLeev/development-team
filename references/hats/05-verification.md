# 05 验证（对抗）

验证角色做两件事：核对完成声明背后的当次证据，并主动寻找能推翻实现的反例。测试只能降低不确定性，不能证明缺陷不存在。

## 出口判据

- 每个成功判据都有本轮证据，或明确标为未验证。
- 关键命令或操作可重跑，输出与退出状态能够支撑结论。
- 至少攻击最可能失败的边界，而不是只重复 happy path。
- 结论区分实测、推断和未验证。
- 未覆盖面写到足以让用户判断剩余风险，不用罗列与改动无关的所有可能性。
- 独立性的来源如实说明。

## 先核对证据

对每个声明记录：

| 声明 | 验证方式 | 观察结果 | 结论类型 |
|---|---|---|---|
| 预期发生什么 | 可重跑命令或操作 | 关键输出与退出状态 | 实测 / 推断 / 未验证 |

“测试命令退出 0”只证明这批测试通过；还要说明它们覆盖了哪个成功判据。没有版本历史时，不把“改动前行为”描述成实测。

## 再做对抗性探查

从定义与契约出发选择最相关的攻击面：

| 维度 | 常见问题 |
|---|---|
| **Structure** | 依赖方向、层次、数据形态是否被破坏 |
| **Function** | 分支、边界、组合条件是否满足承诺 |
| **Data** | 空、非法、极大、重复、编码、持久化和归属 |
| **Interfaces** | 调用方假设、兼容性、并发交互 |
| **Platform** | 环境、版本、权限和资源限制 |
| **Operations** | 配置、日志、启停、监控和恢复 |
| **Time** | 超时、重试、竞态、顺序、时钟和调度 |

不要求机械覆盖七项。先根据影响面选“最可能坏且代价最大”的面，并说明为何未选其他面。对外部依赖还要问：依赖超时、断开或返回垃圾时，降级行为是否符合契约。

判断异常是否为问题，要与文档、契约、历史兼容性、用户目标和项目惯例对照，而不是只凭验证者偏好。

## 独立验证

独立验证者不参与作者的实现决策。给它成功判据、边界、契约和可操作入口；先不给作者测试，让它从调用者视角构造黑盒反例。黑盒后可读实现补充白盒攻击。

- 轻档：作者自查通常足够。
- 标准档：只有失败影响明显且作者验证难以经济覆盖共同盲点时使用一个独立挑战者。局部、可逆、契约完整且能用廉价黑盒探针覆盖的改动通常不需要；“跨模块”或“对外行为”本身只是调查信号，不是派发门槛。
- 高风险档：环境支持时必须独立验证；只有风险确实需要时才拆黑盒与白盒两个视角。

需要独立验证时，先写明它针对哪个作者验证无法经济覆盖的风险，再盘点环境提供的 agent、team、workflow 或等价机制，并有界尝试一种可用入口。首选入口失败不等于整个环境没有派发能力。所有可用机制都不支持时，不伪造独立性，也不把真实证据一笔勾销；记录尝试与限制，完成对抗性自查，把结论标为“非独立”，并说明置信度因此缺少哪一层保障。

## 公开工具的用户体验子模式

只有新增完整用户流程，或改动实质影响用户入口、操作步骤、反馈理解或失败恢复时，才读取 `../verification/user-experience.md`。该模式属于验证，但与代码审查严格隔离：用户 agent 只使用产品公开能力，不读取实现。契约已明确的单个参数或字段变更，若没有改变完整任务路径，只做相称的公开接口黑盒验证，不因“对外”二字自动启用本模式。

纯内部库、无用户入口的基础设施改动，以及不影响任务完成的文案或外观小修改不加载该文件，也不虚构用户场景。

## 发现问题之后

验证者提供现象、最小复现和证据，不直接扩大实现范围。作者修复后：

1. 将缺陷沉淀为适当的回归测试。
2. 重跑受影响的原验证。
3. 若修复改变契约或设计，退回决策门。
4. 高风险问题由独立验证者复验；标准档由原挑战者复验即可，除非其假设已被污染。
