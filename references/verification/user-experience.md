# 用户体验验证（纯黑盒）

本文件是验证角色的条件子模式，不是独立角色。它只判断不知道内部实现的真实用户能否通过公开入口顺利完成目标。

## 触发边界

新的用户产品、工具或完整端到端流程可运行，或现有改动实质影响用户发现入口、完成任务、理解结果或从失败中恢复时触发。契约已明确的单个参数或字段变更，若没有改变完整任务路径，只做相称的公开接口黑盒验证，不自动派发用户 agent。纯内部库、无用户入口的基础设施，以及不影响任务完成的文案或外观小改不触发；这类变化由作者做相称的检查即可。

## 独立性与环境

至少派发两个未参与开发、彼此独立的用户子 agent。每个 agent 使用新的上下文和独立测试环境，不继承实现讨论、源码分析、作者测试、开发调试现场或其他用户 agent 的发现。

每个用户 agent 只获得：

- 一种有现实依据的用户身份与经验水平；
- 一个按结果描述、但不提供正确步骤的任务；
- 产品公开的 UI、CLI、API、插件或工具；
- 普通用户可见的帮助、文档、账户和安全测试数据。

不得读取源码、测试、内部设计或开发日志，不得调用内部函数、私有接口、测试钩子，也不得绕过产品直接访问数据库、缓存、队列或文件状态。产品以工具集合对外时，只能调用已暴露工具。

默认隔离会影响体验的账号、租户、数据、配置、缓存、文件目录、浏览器 profile 和外部服务沙箱。可以共享只读构建或测试部署，但每个 agent 必须从干净状态开始；资源受限时可在每次体验前重置到相同快照。只有验证多人协作或共享状态时，才把指定共享范围作为测试变量。不得在开发者正在调试的环境或生产环境中体验。

## 任务与反馈

按真实受众选择不同视角，不让多个 agent 机械重复同一脚本。通常覆盖首次发现、核心任务，以及一次犯错后的理解与恢复。

每个 agent 只报告用户侧证据：

- 任务成功、失败或阻塞；
- 实际步骤及第一次卡住或需要猜测的位置；
- 工具名称、说明、参数和结果是否易懂；
- 是否存在不必要调用、重复输入或上下文切换；
- 进行中、成功和失败反馈是否及时明确；
- 错误是否说明原因、保留工作并给出可执行下一步；
- 最重要的体验问题与改进建议。

协调者按**阻塞、明显摩擦、主观偏好**汇总，保留分歧和公开复现路径。属于既定目标的问题交回开发方修复；涉及新范围、业务规则或兼容性时退回决策门，不由模拟用户扩展需求。

修复后使用新的用户 agent 和干净环境复测受影响流程，避免已学会路径的 agent 掩盖可发现性问题。结束后清理本轮账户、数据、进程和临时资源。

## 出口判据

- 至少两个独立用户 agent 只通过公开入口完成代表性体验。
- 关键成功、阻塞和摩擦有可复现的用户侧证据。
- 阻塞已修复并由新用户复测，或作为未决事项交回用户。
- 最终说明区分用户实测、开发推断和未验证体验。

若缺少多个隔离子 agent、独立测试环境或安全公开入口，明确标记“用户体验未验证”；不得用开发者操作、内部函数测试或代码审查冒充。
