# 09 用户体验（纯黑盒）

用户体验角色不审查代码，也不证明内部实现正确。它模拟不知道产品内部结构的真实用户，只通过产品公开暴露的入口完成目标，观察产品是否容易发现、理解、操作和恢复。

## 何时触发

在新的用户产品、工具或端到端用户流程已经可运行，并完成基本工程验证后触发。现有产品的改动若改变用户入口、操作步骤、参数、反馈、错误处理或恢复路径，也要触发。

纯内部库、没有可操作用户入口的基础设施改动，以及不改变使用体验的机械编辑不触发。不要为了满足流程给它们编造用户场景。

## 独立性与访问边界

至少派发两个未参与开发、彼此独立的用户子 agent。每个 agent 使用新的隔离上下文和独立测试环境，不继承实现讨论、源码分析、作者测试、开发者调试现场或其他用户 agent 的发现与状态。

用户 agent 只允许获得：

- 一种有现实依据的用户身份与经验水平；
- 一个以结果描述的任务，不提供正确步骤；
- 产品公开的 UI、CLI、API、插件或工具入口；
- 普通用户能够看到的帮助、文档、示例、账户和安全测试数据。

用户 agent 不得：

- 打开源码、测试、内部设计文档或实现提交；
- 直接调用未作为产品能力公开的代码函数；
- 绕过产品访问数据库、文件状态、缓存或消息队列；
- 使用测试钩子、私有接口、调试控制台或开发日志解释结果；
- 因为猜到实现方式而替产品补全缺失步骤。

如果产品以工具集合对外提供能力，用户 agent 只能调用这些已暴露工具。能够通过内部函数完成任务不算用户成功。

## 如何组织体验

根据真实目标选择不同用户视角，不要让多个 agent 机械重复同一条脚本。通常覆盖：

1. **首次使用**：只靠名称、描述和公开帮助找到入口并开始。
2. **核心任务**：用合理步骤完成产品承诺的主要结果。
3. **犯错与恢复**：输入不完整、选择错误或外部条件失败时，理解发生了什么并继续。

小产品可以让两个 agent 分别覆盖首次使用与熟练使用；流程长、受众差异大或失败代价高时再增加角色。不要用虚构 persona 数量代替真实操作。

默认不让用户 agent 共享会改变体验的可变状态。按产品形态隔离账号或租户、数据库或 schema、配置、缓存、文件目录、浏览器 profile、队列和外部服务沙箱；可以共享同一份只读构建产物或测试部署，但每个 agent 应从可复现的干净状态开始。资源受限时，可以为每次体验重置同一测试环境到相同快照，但不能把前一个用户留下的状态带给后一个用户。

只有产品目标本身是多人协作、共享状态或并发交互时，用户 agent 才共享相关环境；把共享范围作为明确的测试变量，其余账号和数据仍应隔离。用户体验不得在开发者正在调试的环境或生产环境中进行。会影响他人、费用或不可逆数据的操作仍需用户授权；不能安全隔离时停止并标记未验证。结束后清理本轮创建的账户、数据、进程和临时资源。

## 每个用户 agent 的反馈

只报告从公开界面观察到的事实和用户判断：

- 任务目标、最终成功 / 失败 / 阻塞；
- 实际尝试的步骤，以及第一次卡住或需要猜测的位置；
- 工具名称、说明、参数和返回结果是否容易理解；
- 完成任务是否需要不必要的调用、重复输入或上下文切换；
- 进行中、成功和失败是否都有及时、明确的反馈；
- 错误提示是否说明原因、保留已有工作并给出可执行的下一步；
- 哪些行为让用户不确定产品状态、后果或是否可以安全重试；
- 最重要的改进建议，以及它解决的具体体验问题。

不要求用户 agent 提出代码方案。它不知道内部实现，正是这项证据的价值。

## 反馈给开发团队

协调者合并多个用户 agent 的观察，保留分歧，不用平均分掩盖阻塞问题。每项反馈至少包含公开复现路径和可观察结果，并分为：

- **阻塞**：代表性任务无法完成，或用户可能造成严重错误；
- **明显摩擦**：可以完成，但发现、理解、步骤或恢复成本不合理；
- **主观偏好**：不妨碍任务完成，且不同用户可能有合理差异。

开发方先处理属于既定产品目标的阻塞和明显摩擦。若反馈意味着改变产品范围、业务规则或兼容性，退回决策门交给用户选择，不由模拟用户扩大需求。

修复后使用新的用户 agent 重跑受影响任务。不要让已经学会正确路径的原 agent 单独证明可发现性已经改善；原 agent 可以补充确认回归，但不能替代新用户复测。

## 出口判据

- 至少两个独立用户 agent 只通过公开产品入口完成了代表性体验。
- 每个 agent 从独立或已重置的干净测试环境开始；任何共享状态都是有意验证的产品行为。
- 关键任务的成功、阻塞和摩擦都有可复现的用户侧证据。
- 阻塞问题已修复并由新用户复测，或作为明确未决事项交给用户。
- 明显摩擦已处理，或记录了不处理的产品理由。
- 最终说明区分用户实测、开发推断与未验证体验。

若环境无法提供多个隔离子 agent、独立测试环境或安全的公开入口，这个角色不能完成。明确写“用户体验未验证”及原因，不用开发者操作、内部函数测试或代码审查冒充。
